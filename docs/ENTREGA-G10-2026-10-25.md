## 4. Diagnóstico do Hermes — `PASS-WITH-CONDITIONS`

**Causa raiz encontrada (não é credencial, não é intermitência aleatória):**

1. O gateway (`nousresearch/hermes-agent`) **serializa turnos por sessão** — log
   `turn_facade_lease.py`: *"Another Hermes process is using this session; waiting…"*.
   Sem `X-Hermes-Session-Id`, requisições independentes entram na **mesma fila**.
2. Meu teste anterior usava `max_tokens` baixo: o agente trunca (`finish_reason='length'`) e pede
   **até 4 continuações**, multiplicando a latência. Foi isso que produziu "66 s" e ">120 s".

**Medições reais (pedido `"Responda apenas: ok"`, sem cap):**

| Cenário | Resultado |
|---|---|
| 1ª chamada (frio) | 200, **25 s**, `choices` válido |
| 2ª chamada (quente) | 200, **6,8 s** |
| 2 concorrentes, mesma sessão | 91 s + 31 s (serializado) |
| 2 concorrentes, sessões distintas | **15,8 s no total** (paralelo) |
| `max_tokens: 1` + timeout 10 s (como o `testProvider` do main) | **TimeoutError em 10 s** |

**Correções aplicadas:**

- `providerHeaders(providerId, correlation)`: envia `x-hermes-session-id: jarvis-<correlação do run>`
  para o Hermes. Estável dentro da execução, distinto entre execuções, sem prompt nem segredo.
- `testProvider`: não envia mais `max_tokens` (media o loop de continuação, não o provedor), usa
  prompt curto e timeout de 30 s, e informa a latência no detalhe.

**Limites que permanecem:** o Hermes é um runtime de agente — 25 s a frio é o piso observado, e o
gateway ainda serializa turnos da **mesma** sessão (correto: é continuidade). Não substituí
resultado do Hermes pelo fallback em nenhum ponto.

### 5.2 Imagem candidata construída e testada (não implantada)

`deploy/crawl4ai-egress-failclosed/Dockerfile` → `crawl4ai-egress:failclosed-g10`, derivada da
**mesma base pinada** (`unclecode/crawl4ai@sha256:bd36741e…`, 0.9.2), com os dois patches
aplicados no build e validação de sintaxe + `EgressNotReady`.

| Caso | Resultado |
|---|---|
| Boot + proxy | OK, `/health` 200 |
| Público | 200 com conteúdo |
| Interno direto (loopback/metadados/LAN) | 400 `URL blocked` |
| Redirect → `127.0.0.1` | bloqueado (proxy 403) |
| Redirect → `localtest.me` (rebinding por nome) | bloqueado |
| Redirect → `169.254.169.254` | bloqueado |
| **WebSocket** `Upgrade` → loopback / metadados | **403** |
| **WSS** `CONNECT` → loopback | **403** |
| `enforce_egress()` sem proxy | **`EgressNotReady`** (fail-closed) |
| Proxy morto (`127.0.0.1:1`) | `proxy_config` aponta para o proxy morto — nunca conexão direta |

**Fail-closed no boot** é estrutural: o `lifespan` inicia o proxy antes de servir; uma exceção ali
aborta o startup (observado na prática quando um patch com nome errado derrubou o worker).

### 5.3 Limites

- `ALLOW_INTERNAL_URLS=true` continua sendo opt-out consciente — deve permanecer `false`.
- WebSocket validado no nível do proxy, não com um servidor WS público real.
- A resolução final continua no serviço remoto até a imagem candidata ser autorizada e implantada.

**Consumidores:** Jarvis (`http://omniroute:20128/v1`), nginx (`proxy_pass http://omniroute:20128`
e `:3012`) — todos por **DNS de serviço**. Nenhum container usa o endereço do host.

**Proposta preparada** (`deploy/omniroute-bindings/`): bind em `127.0.0.1` para 20128 e 3012.
Detalhe técnico relevante: `ports` **acumulam** no merge de Compose — sem `!override` (Compose
≥ 2.24) a restrição não teria efeito. Validado com `docker compose config` (mostra
`host_ip: 127.0.0.1`), sem aplicar nada.

**Risco que a proposta não resolve:** o painel continua exposto **publicamente** em
`omniroute.laytech.com.br` (307 → `/login`; API → 401). Restringir isso é decisão separada
(allowlist no nginx, auth adicional ou remoção do bloco público).

**Efeito colateral a confirmar:** acesso direto ao painel por `http://192.168.4.214:20128` ou
`http://100.87.104.126:20128` deixa de funcionar; o caminho público permanece.

## 11. Checklist de validação após provisionar HTTPS

1. `dig +short jarvis.laytech.com.br` → A/AAAA corretos.
2. `openssl s_client -connect jarvis.laytech.com.br:443 -servername …` → cadeia válida e hostname.
3. `curl -I http://jarvis.laytech.com.br/` → `301` para HTTPS (exceto `/.well-known/acme-challenge/`).
4. `curl -I https://…` → `Strict-Transport-Security` presente; ausente no hop HTTP interno.
5. Renovação: forçar `certbot renew --dry-run` (ou equivalente) e conferir o timer.
6. Login/recarga/logout em HTTPS com `JARVIS_COOKIE_SECURE=1`; conferir `Secure` no `Set-Cookie`.
7. CSRF e `Origin` inválida continuam rejeitados (403).
8. Acesso LAN/tailnet existente não regride.
